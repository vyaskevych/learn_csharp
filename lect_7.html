Мотивація: чому один клас — це погано?

Спробуємо описати автомобіль в одному класі. Що станеться, якщо додати до нього характеристики двигуна?

class Car
{
    public string Model { get; set; }
    
    // Проблема: поля описують іншу сутність!
    public string EngineType { get; set; }
    public int EnginePower { get; set; }
    public double EngineVolume { get; set; }
    public bool EngineRunning { get; set; }

    public void StartEngine()
    {
        EngineRunning = true;
        Console.WriteLine($"{Model}: двигун запущено");
    }
}

Архітектурні проблеми

  • Зростання класу: Додамо коробку передач, колеса, гальма — і отримаємо «Божественний об'єкт» (God Object).
  • Дублювання: Для створення мотоцикла доведеться переписувати всю логіку двигуна наново.

Рішення: Декомпозиція та об'єкт як поле

Виносимо характеристики двигуна в окремий повноцінний клас Engine. 

class Engine
{
    public string Type { get; }
    public int Power { get; }
    public bool IsRunning { get; private set; }

    public Engine(string type, int power)
    {
        Type = type;
        Power = power;
    }

    public void Ignite()
    {
        IsRunning = true;
        Console.WriteLine($"Двигун {Type} запущено");
    }
}

Головна ідея

Тип поля класу може бути не лише базовим (int, string), а й іншим створеним вами класом.

Так формується відношення «HAS-A» (має у складі).

Види зв'язку «HAS-A»

В об'єктно-орієнтованому проєктуванні відношення включення поділяють на три рівні за ступенем залежності об'єктів:

1. Асоціація (Association)

Слабкий зв'язок. Об'єкти просто взаємодіють (наприклад, Водій і Автомобіль), але існують повністю незалежно.

2. Агрегація (Aggregation)

Відношення «частина-ціле». Частина передається ззовні і може існувати окремо після знищення цілого (наприклад, Автопарк і Автомобіль).

3. Композиція (Composition)

Жорстке відношення «частина-ціле». Ціле саме створює частину, і вона не може існувати без нього (наприклад, Автомобіль і Двигун).

Асоціація: UML-нотація та реалізація

Асоціація — найслабший зв'язок, де об'єкти існують незалежно.

Суцільна лінія зі стрілкою: об'єкт передається як параметр у метод іншого.

class Car
{
    public string Model { get; }
    public Car(string model) => Model = model;
    public void Move() => Console.WriteLine($"{Model} їде.");
}

class Driver
{
    public string Name { get; }
    public Driver(string name) => Name = name;

    // Асоціація: тимчасове використання
    public void Drive(Car car)
    {
        Console.WriteLine($"{Name} керує {car.Model}");
        car.Move();
    }
}

Агрегація: UML-нотація та реалізація

Агрегація — частина створюється ззовні і передається всередину.

Лінія з порожнім ромбом. Автомобіль може існувати без автопарку.

class Fleet
{
    public string CompanyName { get; }
    private Car companyCar; // Поле-посилання

    // Агрегація: Car створюється ззовні
    public Fleet(string name, Car car)
    {
        CompanyName = name;
        this.companyCar = car; 
    }

    public void StartWork()
    {
        companyCar.Move();
    }
}

Композиція (Composition): UML-нотація та код

При композиції цілий об'єкт сам створює компоненти через оператор new.

В UML позначається лінією із зафарбованим (чорним) ромбом.

class Car
{
    public string Model { get; }
    private Engine engine; // Сховане поле

    public Car(string model, int power)
    {
        Model = model;
        // Композиція: Car САМ створює Engine
        this.engine = new Engine(power); 
    }
}

Делегування та принцип «Чорного ящика»

Маючи композицію, зовнішній об'єкт може передоручати (делегувати) виконання завдань своїм внутрішнім компонентам.

class Car
{
    public string Model { get; }
    private Engine engine; 

    public Car(string model, int power)
    {
        Model = model;
        this.engine = new Engine(power);
    }

    // Делегування: Car не виконує запуск сам, а просить про це engine
    public void Start()
    {
        Console.WriteLine($"{Model} готується до старту...");
        engine.Ignite(); // Делегування виконання внутрішньому об'єкту
    }
}

// У Main: Водій взаємодіє лише з автомобілем ("чорний ящик")
Car myCar = new Car("Audi", 250);
myCar.Start();

Принцип «IS-A» (Inheritance): Наслідування та UML

Коли між класами існує відношення «є чимось» (наприклад, Собака є Твариною), використовують наслідування.

В UML наслідування позначається лінією з порожнім трикутником.

// Базовий клас (Superclass)
class Animal
{
    public string Name { get; set; }
    public void Eat() { Console.WriteLine("Їсть"); }
}

// Похідні класи (Subclasses)
class Dog : Animal
{
    public void Bark() { Console.WriteLine("Гавкає"); }
}

class Cat : Animal
{
    public void Meow() { Console.WriteLine("Нявкає"); }
}

Практичний приклад: Годинник і Точний годинник

Класичний приклад ієрархії: клас MyPreciseClock успадковує MyClock, додаючи облік секунд до існуючих годин і хвилин.

public class MyClock
{
    public int hours;
    public int minutes;
    
    public void nextMinute()
    {
        minutes++;
        if (minutes >= 60)
        {
            hours++;
            minutes = 0;
            if (hours >= 24) hours = 0;
        }
    }
}
// Похідний клас успадковує MyClock
public class MyPreciseClock : MyClock
{
    public int seconds;

    public void nextSecond()
    {
        seconds++;
        if (seconds >= 60)
        {
            seconds = 0;
            // Викликаємо метод базового класу!
            nextMinute(); 
        }
    }
}

Перетворення типів: Upcasting (Висхідне)

Об'єкти похідного типу (який знаходиться внизу ієрархії) одночасно представляють і базовий тип. Це природно, адже кожен точний годинник є годинником.

Висхідне перетворення (Upcasting) відбувається автоматично і безпечно.

// Створюємо об'єкт дочірнього класу
MyPreciseClock preciseClock = new MyPreciseClock();

// Автоматичне висхідне перетворення (Upcasting) до базового типу
MyClock clock = preciseClock; 

// Через змінну 'clock' ми бачимо ЛИШЕ методи базового класу
// (hours, minutes, nextMinute). Ми не маємо доступу до seconds, 
// хоча в пам'яті це все ще той самий точний годинник!
clock.nextMinute();

Перетворення типів: Downcasting (Низхідне)

Низхідне перетворення (від базового типу до похідного) не виконується автоматично, оскільки не кожен базовий годинник є точним.

MyClock simpleClock = new MyClock();

// ❌ ПОМИЛКА КОМПІЛЯЦІЇ
// MyPreciseClock pc1 = simpleClock; 

// ❌ ПОМИЛКА ВИКОНАННЯ (InvalidCastException)
// Ми примусово змушуємо компілятор повірити,
// що це PreciseClock, хоча це не так.
MyPreciseClock pc2 = (MyPreciseClock)simpleClock;

⚠️ Небезпека Downcasting

Якщо виконати приведення несумісних типів, програма аварійно зупиниться з винятком System.InvalidCastException.

Безпечне перетворення: Оператор is

Щоб запобігти помилці InvalidCastException, необхідно перевіряти фактичний тип об'єкта під час виконання програми за допомогою оператора is.

MyClock someClock = GetClockFromSomewhere();

// Перевіряємо, чи ДІЙСНО в цій змінній лежить об'єкт MyPreciseClock
if (someClock is MyPreciseClock)
{
    // Тепер низхідне перетворення (Downcasting) абсолютно безпечне
    MyPreciseClock precise = (MyPreciseClock)someClock;
    
    // Можемо працювати зі специфічними методами нащадка
    precise.nextSecond();
}
else
{
    Console.WriteLine("Це звичайний годинник, він не має секунд.");
}

Інкапсуляція в ієрархії: protected

Похідні класи успадковують усі члени базового класу, але не мають прямого доступу до його private полів. Для цього існує проміжний рівень доступу.

class Shape
{
    // protected доступний всередині класу 
    // та у всіх класах-нащадках
    protected double width;
    protected double height;
}

class Rectangle : Shape
{
    public void SetSize(double w, double h)
    {
        width = w;  // ✅ Доступ дозволено нащадку
        height = h;
    }
}

Рівні доступу

  • public — доступно всім.
  • protected — доступно лише нащадкам і самому класу.
  • private — доступно лише всередині самого класу (нащадки не бачать).

Порядок виклику конструкторів

В ієрархії класів конструктори викликаються суворо від базового класу до похідного (згори донизу). Спочатку закладається фундамент!

class A
{
    public A() { Console.WriteLine("Конструктор А"); }
}

class B : A
{
    public B() { Console.WriteLine("Конструктор В"); }
}

class C : B
{
    public C() { Console.WriteLine("Конструктор С"); }
}
static void Main()
{
    // Створюємо об'єкт найнижчого класу
    C obj = new C(); 
}

/* РЕЗУЛЬТАТ ВИКОНАННЯ:
Конструктор А
Конструктор В
Конструктор С
*/

Навіть без явної вказівки завжди викликається конструктор за замовчуванням (без параметрів) з базового класу.

Ключове слово base: Передача параметрів батьку

Якщо конструктор базового класу вимагає параметри, похідний клас зобов'язаний передати їх за допомогою ключового слова base.

class Person
{
    public string Name { get; }
    public Person(string name) { Name = name; } // Базовий конструктор
}

class Employee : Person
{
    public string Company { get; }

    // Передаємо параметр name "нагору" у конструктор батька
    public Employee(string name, string company) : base(name)
    {
        Company = company;
    }
}

Звернення до методів батька через base

Ключове слово base також дозволяє викликати оригінальну реалізацію методу з базового класу, якщо похідний клас його перевизначає.

class Person
{
    public virtual void GetInfo() { Console.WriteLine("Person Info"); }
}

class Employee : Person
{
    public override void GetInfo()
    {
        // Викликаємо оригінальний метод батьківського класу
        base.GetInfo(); 
        
        // Додаємо специфічну логіку нащадка
        Console.WriteLine("Employee Info");
    }
}

Золоте правило архітектури ООП

"Favor composition over inheritance"

Надавай перевагу композиції перед наслідуванням.

Чому наслідування буває небезпечним?

Воно створює жорстку зв'язність між класами. Зміна базового класу може непередбачувано зламати всю ієрархію нащадків (проблема "крихкого базового класу").

Чому композиція краща?

Вона робить систему гнучкою, дозволяє легко підміняти компоненти «на льоту» та забезпечує надійну інкапсуляцію.

Висновки

1. Архітектурна декомпозиція

Складні системи проєктуються через розбиття монолітних класів на менші сутності та налаштування зв'язків між ними.

2. Ієрархія зв'язків «HAS-A»

Асоціація (слабкий зв'язок), Агрегація (передача частини ззовні) та Композиція (створення частини всередині через new).

3. Принцип «IS-A» (Наслідування)

Дозволяє будувати ієрархії, створюючи спеціалізовані класи на основі базових, розширюючи їх функціонал та уникаючи дублювання коду.

4. Перетворення типів (Casting)

Висхідне перетворення (Upcasting) є природним і безпечним, тоді як низхідне (Downcasting) вимагає обов'язкової перевірки оператором is.
