Де прихована архітектурна проблема?

У Main() одночасно є Console.ReadLine(), перевірка назви та books.Add(book). У чому головний недолік?

A. Метод має більше ніж один оператор if.

B. Поєднано різні причини для змін в одному місці.

C. Використано колекцію List<Book>.

D. Метод написаний у консольному застосунку.

Правильна відповідь: B.

  • A — хибно: Кількість умов не визначає кількість відповідальностей.
  • B — правильно: Введення, перевірки й керування даними змінюються з різних причин.
  • C — хибно: Сам List<T> — допустиме сховище для навчального прикладу.
  • D — хибно: Консоль допустима як UI; проблема — її змішування з логікою каталогу.

Single Responsibility Principle (SRP)

Принцип єдиної відповідальності

Клас має представляти одну узгоджену сферу поведінки й мати одну основну причину для змін.

Одна відповідальність

Керування каталогом книг.

Різні відповідальності

Керування каталогом і форматування консольного меню.

SRP — один із принципів SOLID, а не вимога «один метод на клас».

Куди перенести PrintMenu()?

Клас BookCatalog містить методи Delete() і PrintMenu(). Яка зміна найкраще відповідає SRP?

A. Винести Delete() у Book.

B. Винести PrintMenu() у ConsoleView.

C. Залишити обидва методи, але зробити їх static.

D. Перемістити обидва методи до Program.cs.

Правильна відповідь: B.

  • A — хибно: Модель книги не повинна керувати видаленням із каталогу.
  • B — правильно: Меню належить до взаємодії з користувачем; CRUD залишається в сервісі.
  • C — хибно: Статичність не усуває змішування відповідальностей.
  • D — хибно: Перенесення в точку запуску знову змішує UI та CRUD.

Хто має обробляти введене Id?

Користувач увів текст "abc" замість номера книги. Яка частина застосунку повинна обробити невдале перетворення рядка на число?

A. Book, бо книга має Id.

B. BookCatalog.Read(), бо виконує пошук.

C. ConsoleView, бо працює з введенням користувача.

D. Program.cs, бо запускає застосунок.

Правильна відповідь: C.

  • A — хибно: Модель забезпечує коректність власного стану, а не розбирає консольне введення.

  • C — правильно: UI зчитує текст і може застосувати int.TryParse перед викликом сервісу.
  • D — хибно: Точка запуску лише створює та поєднує об’єкти.

Book.cs: структура моделі

У нашому прикладі властивості доступні тільки для читання ззовні; перевірки виконуються під час створення об’єкта.

public class Book
{
    public int Id { get; }
    public string Title { get; }
    public string Author { get; }

    public Book(int id, string title, string author)
    {
        if (id <= 0)
            throw new ArgumentOutOfRangeException(nameof(id));
        if (string.IsNullOrWhiteSpace(title))
            throw new ArgumentException("Назва не може бути порожньою.");
        if (string.IsNullOrWhiteSpace(author))
            throw new ArgumentException("Автор не може бути порожнім.");

        Id = id;
        Title = title.Trim();
        Author = author.Trim();
    }

    public override string ToString() => $"{Id} | {Title} | {Author}";
}

Service: Create()

Перевірка параметрів передує створенню нового екземпляра й збільшенню _nextId.

public Book? Create(string title, string author)
{
    if (string.IsNullOrWhiteSpace(title) ||
        string.IsNullOrWhiteSpace(author))
        return null;

    Book book = new Book(_nextId, title, author);
    _books.Add(book);
    _nextId++;
    return book;
}

Результат — нова книга або null. Сервіс не виводить текст повідомлення.

Service: Update()

Модель Book у цьому прикладі незмінювана через публічний API, тому оновлення замінює елемент новим екземпляром.

public bool Update(int id, string newTitle, string newAuthor)
{
    if (string.IsNullOrWhiteSpace(newTitle) ||
        string.IsNullOrWhiteSpace(newAuthor))
        return false;

    int index = _books.FindIndex(book => book.Id == id);
    if (index == -1) return false;

    _books[index] = new Book(id, newTitle, newAuthor);
    return true;
