План лекції

1. Проблема відкритого стану

Чому використання публічних полів порушує цілісність даних та вважається антипатерном.

2. Інкапсуляція та модифікатори доступу

Приховування реалізації (`private`) та створення публічного інтерфейсу (`public`). UML-нотація.

3. Властивості (Properties) та валідація

Розумний доступ до даних через аксесори `get` та `set`. Ключове слово `value`.

4. Сучасний синтаксис C#

Авто-властивості, expression-bodied members (`=>`), створення незмінних об'єктів (`init`, `required`).

5. Статичні члени та класи (`static`)

Різниця між пам'яттю конкретного об'єкта та спільною пам'яттю типу.

Чому public поля — це антипатерн?

Якщо стан об'єкта (поля) повністю відкритий, компілятор дозволить записати туди будь-які математично можливі, але логічно абсурдні значення.

Архітектурна вразливість

Компілятор не знає бізнес-логіки вашої програми. Для нього змінна width типу double може приймати будь-які від'ємні значення, хоча фізично коробка не може мати від'ємну ширину. 

class Box
{
    // Відкритий стан
    public double width;
    public double height;
}

// У методі Main:
Box parcel = new Box();

// Синтаксично правильно, 
// логічно - катастрофа!
parcel.width = -15.5; 
parcel.height = 0;

Інкапсуляція ("Чорний ящик")

Визначення

Інкапсуляція — це принцип приховування внутрішнього стану та деталей реалізації об'єкта. Взаємодія з ним відбувається виключно через чітко визначений "публічний інтерфейс".

Метафора: Банкомат

Ви (користувач) не маєте прямого доступу до касет із грошима всередині банкомату.

Взаємодія йде через клавіатуру та екран, а банкомат сам вирішує, чи дозволити операцію (перевіряючи ПІН-код та залишок на балансі).

Проєкція на код

  • Прихований стан: Змінні (поля) класу. Це наші касети з грошима.
  • Публічний інтерфейс: Дозволені методи (Властивості). Це клавіатура та екран.

Керування доступом: private та public

private (Приватний)

Член класу доступний тільки всередині цього ж класу. Це наші надійно сховані дані. (У C# застосовується за замовчуванням).

public (Публічний)

Член класу доступний звідусіль (з методу Main, з інших класів тощо). Це відкрита поведінка об'єкта.

class Box
{
    // 1. Прихований стан (дані в безпеці)
    private double width; 
    private double height;
    
    // 2. Метод доступний всім
    public double GetVolume() 
    {
        return width * height * depth; // Має доступ до своїх private полів
    }
}
// parcel.width = -15.5; // ❌ ПОМИЛКА КОМПІЛЯЦІЇ!

Конструктори та методи Get/Set

Якщо поля закриті (private), як змінити їх значення ззовні? Класичний підхід (використовується в Java та C++) вимагає створення спеціальних методів-посередників.

class Box
{
    private double width; // Поле сховано

    // Метод для безпечного ЗАПИСУ (з валідацією)
    public void SetWidth(double w)
    {
        if (w > 0) this.width = w;
    }

    // Метод для безпечного ЧИТАННЯ
    public double GetWidth() 
    {
        return this.width; 
    }
}

Проблема: Працювати з такими методами незручно. Замість звичного box.width = 10; доводиться писати box.SetWidth(10);. Код стає громіздким.

Розумний доступ: Властивості у C#

Властивість (Property) — це гібрид. Зовні вона виглядає та використовується як звичайне поле (через знак =), але всередині містить приховані методи для безпечного читання та запису даних.

class Box
{
    private double width; // Backing field (Реальне сховище)

    public double Width   // Публічна властивість (Шлюз безпеки)
    {
        get { return this.width; } // Спрацює при читанні
        
        set // Спрацює при записі
        { 
            // value - приховане ключове слово для вхідного значення
            if (value > 0) this.width = value; 
        }
    }
}

Використання: box.Width = 15; — викликає блок set, де змінна value дорівнює 15.

Промислова валідація даних

У реальних проєктах використання Console.WriteLine всередині класів бізнес-логіки суворо заборонено (клас не повинен знати про консоль). Інженери використовують генерацію винятків (Exceptions). 

public double Width
{
    get { return this.width; }
    set 
    { 
        if (value <= 0) 
        {
            // Жорстко зупиняємо виконання та сигналізуємо про помилку
            throw new ArgumentException("Ширина має бути більшою за нуль!"); 
        }
            
        this.width = value; 
    }
}

Якщо програміст спробує написати box.Width = -5;, програма аварійно завершиться із чітким описом архітектурного порушення.

Практичний приклад: Захист даних у класі Pen

Розглянемо клас ручки (`Pen`), де за допомогою властивості Color реалізовано захист від некоректних даних.

class Pen
{
    private string color; // Закрите поле для зберігання стану

    public string Color   // Публічна властивість з логікою перевірки
    {
        get { return color; }
        set
        {
            // Якщо код кольору не має 6 символів — встановлюємо чорний за замовчуванням
            if (value.Length != 6) 
            { 
                color = "000000"; 
            }
            else 
            {
                color = value; 
            }
        }
    }
}

Як це працює: Прямий доступ до поля color заблоковано (`private`). Користувач взаємодіє лише з властивістю Color, а об'єкт самостійно гарантує, що у поле ніколи не потрапить шкідливе чи помилкове значення.

Скорочений синтаксис (=>)

У C# є зручний синтаксис Expression-bodied members. Якщо ваша властивість призначена ТІЛЬКИ для читання (не має set) і містить лише один вираз, код можна значно скоротити.

class Rectangle
{
    private double width = 10;
    private double height = 5;

    // Класичний довгий запис (Read-Only властивість):
    public double AreaClassic
    {
        get { return width * height; }
    }

    // Сучасний скорочений запис за допомогою "лямбди" (=>):
    public double AreaModern => width * height;
}

Цей підхід ідеально підходить для обчислюваних властивостей, які не зберігають дані фізично, а розраховують їх "на льоту" на основі інших полів.

Авто-властивості (Auto-properties)

Якщо валідація даних вам поки що не потрібна, немає сенсу вручну створювати приховане поле та писати базові get/set. Компілятор може зробити цю рутину за вас.

class Order
{
    // Компілятор сам створить приховане поле "під капотом"
    public string CustomerName { get; set; }
    
    // Властивість з початковим значенням
    public string Status { get; set; } = "New";

    // Прочитати можуть всі, а змінити - ТІЛЬКИ всередині цього класу
    public int OrderId { get; private set; } 

    public Order(int id)
    {
        OrderId = id; // Це працює завдяки private set
    }
}

Питання зі співбесіди: Властивості vs Поля

"Чому авто-властивість { get; set; } краща за звичайне відкрите поле, якщо візуально вони діють абсолютно однаково?"

// ПОГАНА ПРАКТИКА:
public string Name;

// СУЧАСНИЙ СТАНДАРТ:
public string Name { get; set; }
  • Майбутня гнучкість: До властивості можна легко додати логіку перевірки пізніше без порушення бінарної сумісності з іншим кодом.
  • Data Binding (Прив'язка даних): Такі технології як Entity Framework Core (Бази даних) або WPF (Інтерфейси) вміють працювати лише з властивостями.
  • Інтерфейси: C# дозволяє вимагати наявність властивостей в інтерфейсах, але не полів.

Сучасний C#: Безпека та Незмінність

Сучасний архітектурний тренд — створення незмінних (immutable) об'єктів. Для цього у C# з'явилися інструменти init та required.

class ModernUser
{

    public required string Username { get; init; }

{
    static void Main()
    {
        // Успішне створення об'єкта через ініціалізатор
        ModernUser user = new ModernUser { Username = "admin" };
        
        // ❌ ПОМИЛКА КОМПІЛЯЦІЇ: init блокує зміну даних!
        // user.Username = "hacker"; 
    }
}

Пам'ять об'єкта vs Пам'ять типу (static)

Зазвичай кожна властивість належить конкретному екземпляру. Однак іноді нам потрібні дані, спільні для всього креслення (класу). Для цього використовують ключове слово static.

Звичайні поля (Екземпляр)

  • Належать конкретній деталі.
  • Зміна ширини однієї коробки не впливає на іншу коробку.
  • Звернення: box1.Width

Статичні поля (Клас)

  • Належать самому кресленню.
  • Існують в єдиному екземплярі, діляться між усіма об'єктами.
  • Звернення: Box.TotalCount

Робота зі статичними полями

Класичний приклад використання static — створення глобального лічильника створених екземплярів класу.

class Box
{
    // Ця властивість належить всьому класу Box
    public static int TotalBoxesCreated { get; private set; }

    public Box() 
    { 
        // При кожному виклику конструктора збільшуємо спільний лічильник
        TotalBoxesCreated++; 
    }
}

// У методі Main:
Box b1 = new Box();
Box b2 = new Box();

// Виклик відбувається через ім'я КЛАСУ, а не змінної b1 чи b2!
Console.WriteLine(Box.TotalBoxesCreated); // Виведе 2

Правило ізоляції static

⚠️ Критичне обмеження

Оскільки статичний метод викликається на рівні всього класу, він нічого не знає про конкретні екземпляри.

class Box
{
    public double Width { get; set; } // Звичайна властивість

    public static void PrintInfo()
    {
        // ❌ ПОМИЛКА КОМПІЛЯЦІЇ!
        // Статичний метод не знає, ширину ЯКОЇ САМЕ коробки треба вивести
        // Console.WriteLine(Width);

        // У статичному контексті не існує ключового слова this
        // Console.WriteLine(this.Width); 
    }
}

Статичні класи (static class)

Якщо ваш клас містить тільки глобальні функції або константи, його роблять статичним. Створити об'єкт (new) такого класу неможливо.

public static class MathHelper
{
    // Всі члени всередині статичного класу ТАКОЖ мають бути статичними
    public static double PI = 3.14159;
    
    public static double Square(double number)
    {
        return number * number;
    }
}

// Використання без оператора new:
double result = MathHelper.Square(5);
Console.WriteLine(MathHelper.PI);

// Ви постійно використовували статичні класи раніше:
// Console.WriteLine(), Math.Round(), Array.Sort()

Практичний тест 1: Що виведе код?

Проаналізуйте фрагмент коду зі статичним полем та спробуйте передбачити результат:

class Keeper
{
    public static int b;
    public int getB() { return b; }
}

class Program
{
    static void Main(string[] args)
    {
        int c = Keeper.b++;
        int cc = new Keeper().getB();
        Console.WriteLine(c + " " + cc);
    }
}

Розбір тесту 1: Відповідь

Результат виконання: 0 1

Покроковий розбір:

  • Статичне поле Keeper.b за замовчуванням ініціалізується нулем (0).
  • У рядку int c = Keeper.b++; через постфіксний інкремент змінна c спочатку отримує поточне значення (0), а потім поле b збільшується до 1.
  • Створений об'єкт new Keeper().getB() звертається до цього ж спільного статичного поля і повертає актуальне значення — 1.

Практичний тест 2: Що виведе код?

Визначте значення змінних c та cc після виконання програми:

class Program
{
    static int a = 10;
    static int b = a;

    static void Main(string[] args)
    {
        int c = ++a;
        int cc = b++;
        Console.WriteLine(c + " " + cc + " ");
    }

Основні архітектурні правила

1. Захист стану (Інкапсуляція)

Усі поля класу повинні бути закриті (private). Відкритий доступ до даних здійснюється виключно через публічні властивості.

2. Властивості та валідація

Властивості (get/set) забезпечують контроль за даними, що надходять через змінну value. Авто-властивості є галузевим стандартом.

3. Незмінність об'єктів

Використання модифікатора init дозволяє створити надійні об'єкти, стан яких неможливо змінити після завершення ініціалізації.

4. Правила статичності

static застосовується для створення спільного контексту типу. У статичних методах немає доступу до ключового слова this та нестатичних членів.
