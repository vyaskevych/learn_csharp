Що таке поліморфізм?

Визначення

Поліморфізм (від грец. poly — багато, morph — форма) — це принцип ООП, який дозволяє сутностям (змінним, функціям або об'єктам) мати різні форми або по-різному реалізовувати одну й ту саму дію.

1. Статичний (Раннє зв'язування)

Вирішується компілятором до запуску програми.

Реалізується через перевантаження методів: методи мають однакове ім'я, але різну кількість або типи параметрів.

2. Динамічний (Пізнє зв'язування)

Вирішується середовищем виконання (CLR) під час роботи програми.

Реалізується через перевизначення методів: об'єкти-нащадки змінюють логіку методів базового класу.

Статичний поліморфізм (Перевантаження)

Наочний приклад статичного поліморфізму: один метод, але з різними "формами" прийняття даних.

class Printer
{
    // Форма 1: друкує ціле число
    public void Print(int number) 
    {
        Console.WriteLine($"Друк числа: {number}");
    }

    // Форма 2: друкує рядок
    public void Print(string text) 
    {
        Console.WriteLine($"Друк тексту: {text}");
    }
}

// Використання (компілятор одразу знає, який метод викликати):
Printer p = new Printer();
p.Print(100);       // Викличе Форму 1
p.Print("Hello");   // Викличе Форму 2

Проблема: Антипатерн перевірки типів

Уявімо розробку системи сповіщень. У нас є незалежні класи з різними методами. Якщо не використовувати динамічний поліморфізм для їх об'єднання, розробники часто пишуть жахливі конструкції з перевіркою типів (оператор is).

// 1. Існуючі незалежні класи (не мають спільного предка)
class EmailNotifier { 
    public void SendEmailMessage() { /* Логіка пошти */ } 
}
class TelegramNotifier { 
    public void SendTelegramBot() { /* Логіка Telegram */ } 
}

class SystemController
{
    // 2. Намагаємося обробити їх єдиним списком об'єктів (object)
    public void SendAllNotifications(object[] notifiers)
    {
        foreach (var notifier in notifiers)
        {
            // Жорстка прив'язка: перевіряємо тип і викликаємо специфічний метод
            if (notifier is EmailNotifier)
            {
                ((EmailNotifier)notifier).SendEmailMessage();
            }
            else if (notifier is TelegramNotifier)
            {
                ((TelegramNotifier)notifier).SendTelegramBot();
            }
            // А що, якщо завтра бізнес попросить додати SMS? Доведеться переписувати цей цикл!
        }
    }
}

Чому такий підхід руйнує архітектуру?

Порушення OCP (Open-Closed Principle)

Система має бути відкритою для розширення (додавання нових функцій), але закритою для модифікації (зміни старого робочого коду).

  • Крихкість: Кожного разу, коли з'являється новий канал зв'язку (Viber, SMS, Push), розробник мусить знаходити всі подібні цикли в системі та додавати нові гілки else if.
  • Ризик помилок: Якщо розробник забуде оновити хоча б один такий цикл, новий тип сповіщень просто проігнорується.
  • Висока зв'язність: Клас SystemController змушений "знати" про існування всіх конкретних класів сповіщень.

Рішення: Динамічний поліморфізм

Замість того, щоб система перевіряла тип об'єкта, ми просто наказуємо об'єкту виконати дію. А як саме її виконати — об'єкт вирішує сам.

virtual (у базовому класі)

Створює "точку розширення". Дозволяє (але не зобов'язує) змінити поведінку методу в класах-спадкоємцях.

override (у класі-нащадку)

Явно вказує компілятору: "Я перевизначаю логіку базового методу власною реалізацією".

Повний приклад (Крок 1: Архітектура)

// 1. Базовий клас створює універсальний контракт (метод Send)
public class Notifier
{
    public virtual void Send(string msg) 
    {
        Console.WriteLine($"Базове системне сповіщення: {msg}");
    }
}

// 2. Нащадок 1: Реалізує відправку по Email
public class EmailNotifier : Notifier
{
    public override void Send(string msg) 
    {
        Console.WriteLine($"[EMAIL] Відправка листа на сервер: {msg}");
    }
}

// 3. Нащадок 2: Реалізує відправку в Telegram
public class TelegramNotifier : Notifier
{
    public override void Send(string msg) 
    {
        Console.WriteLine($"[TELEGRAM] Виклик API бота: {msg}");
    }
}

Повний приклад (Крок 2: Використання)

Тепер нам не потрібні конструкції if-else. Магія поліморфізму в тому, що середовище виконання (CLR) самостійно викличе потрібний override метод.

class Program
{
    static void Main()
    {
        // Групуємо об'єкти під посиланням їхнього базового типу
        Notifier[] notifiers = new Notifier[] 
        { 
            new EmailNotifier(), 
            new TelegramNotifier(),
            new Notifier() // Навіть базовий клас спрацює коректно
        };

        // Цей код ідеальний. Він ЗАКРИТИЙ для змін.
        foreach (Notifier item in notifiers)
        {
            item.Send("Успішний вхід!"); 
        }
    }
}

Тріумф архітектури

Результат роботи програми:

[EMAIL] Відправка листа на сервер: Успішний вхід!
[TELEGRAM] Виклик API бота: Успішний вхід!
Базове системне сповіщення: Успішний вхід!

Якщо завтра з'явиться SmsNotifier, вам потрібно буде лише:

  1. Створити новий клас SmsNotifier : Notifier.
  2. Написати override void Send().
  3. Додати його у масив.

Головний цикл відправки не зміниться на жоден символ! Це і є професійне використання поліморфізму.

Проблема базового класу

Наш Notifier вирішив проблему поліморфізму, але створив іншу. З точки зору бізнес-логіки, об'єкта "просто сповіщення" в реальному світі не існує. Воно має бути конкретним (Email, SMS).

public class Shape 
{
    // Що саме має малювати цей метод? У просто "фігури" немає форми!
    public virtual void Draw() 
    { 
        Console.WriteLine("Малюю... незрозуміло що.");
    }
}

// Проблема 1: Ми можемо створити об'єкт-привид
Shape ghost = new Shape();
ghost.Draw(); 

// Проблема 2: Метод virtual ДОЗВОЛЯЄ перевизначення, але НЕ ВИМАГАЄ його.
// Програміст може створити клас Circle і забути написати override.

Рішення: Абстрактні класи

Абстрактний клас (ключове слово abstract) — це концептуальний шаблон або "креслення". Створити прямий екземпляр (об'єкт) абстрактного класу неможливо.

  • Створюються виключно для того, щоб бути базовими класами для інших.
  • Можуть містити як звичайні методи (зі спільною логікою), так і абстрактні методи.
  • Заборона: Shape s = new Shape(); викличе помилку компіляції.
12 / 24

Абстрактні методи

Абстрактний метод — це вимога. Він оголошується без тіла (замість фігурних дужок ставиться крапка з комою) і діє як строгий контракт для нащадків.

Правила:

  1. Будь-який клас-нащадок зобов'язаний реалізувати абстрактний метод (через override). Інакше код не скомпілюється.
  2. Якщо клас має хоча б один абстрактний метод, сам клас теж мусить бути оголошений як abstract.
  3. Абстрактні методи не можуть бути private.
public abstract class Shape
{
    // Абстрактний метод: тіла немає!
    public abstract void Draw(); 
}

Повний приклад абстрактного класу

public abstract class Shape
{
    // Абстрактні класи можуть мати поля та звичайні властивості
    public string Color { get; set; } 

    public Shape(string color) { Color = color; }

    // Звичайний метод (допускається)
    public void PrintColor() => Console.WriteLine($"Колір: {Color}");

    // АБСТРАКТНИЙ МЕТОД (строгий контракт)
    public abstract double GetArea(); 
}

public class Circle : Shape
{
    public double Radius { get; set; }

    public Circle(string color, double r) : base(color) { Radius = r; }

    // ЯКЩО НЕ НАПИСАТИ ЦЕЙ МЕТОД - БУДЕ ПОМИЛКА КОМПІЛЯЦІЇ
    public override double GetArea() 
    {
        return Math.PI * Radius * Radius;
    }
}

Чому C# забороняє множинне успадкування?

Проблема ромба (Diamond Problem)

Уявіть, що C# дозволяв би класу мати кілька базових класів-батьків. Що станеться, якщо обидва батьки мають метод з однаковим іменем, але різною логікою?

class Machine { 
    public virtual void Move() => Console.WriteLine("Їде на колесах"); 
}

class Bird { 
    public virtual void Move() => Console.WriteLine("Махає крилами"); 
}

// ГІПОТЕТИЧНИЙ КОД (В C# ЦЕ ПОМИЛКА КОМПІЛЯЦІЇ):
class Drone : Machine, Bird 
{
    // Дрон успадкував обидва класи
}

Drone myDrone = new Drone();
myDrone.Move(); // 💥 КРАШ! ЧИЙ МЕТОД ВИКЛИКАТИ?
  • Фатальна неоднозначність: Компілятор фізично не здатний вирішити, чию саме реалізацію методу Move() треба виконати — Machine чи Bird.
  • Архітектурний хаос: Чим глибша ієрархія класів, тим більше таких нерозв'язних конфліктів виникає.
  • Рішення C#: Клас може мати ТІЛЬКИ ОДНОГО батька (сувора ієрархія IS-A). А для об'єднання різних ролей і поведінок (CAN-DO) існують Інтерфейси.

Інтерфейси: Контракти поведінки

Інтерфейс (interface) — це структура, яка містить лише оголошення методів та властивостей (без їх реалізації). Якщо клас (IS-A) визначає, чим є об'єкт, то інтерфейс (CAN-DO) визначає, що він вміє робити.

  • Конвенція: Імена завжди починаються з великої I (наприклад, IFlyable, IPrinter).
  • Клас може реалізовувати безліч інтерфейсів одночасно.
  • Усі члени інтерфейсу за замовчуванням є public. Писати модифікатори доступу всередині заборонено.

Приклад реалізації інтерфейсу

// Оголошення контракту поведінки (без реалізації)
public interface IFlyable
{
    void TakeOff();
    int MaxAltitude { get; }
}

// Птах успадковується від тварини, але ВМІЄ літати
public class Bird : Animal, IFlyable
{
    // Обов'язкова реалізація контракту
    public int MaxAltitude => 500;
    public void TakeOff() => Console.WriteLine("Птах махає крилами.");
}

// Дрон успадковується від машини, але ТЕЖ ВМІЄ літати
public class Drone : Machine, IFlyable
{
    // Реалізація того ж самого контракту, але іншим чином
    public int MaxAltitude => 3000;
    public void TakeOff() => Console.WriteLine("Дрон запускає пропелери.");
}

Поліморфізм через інтерфейси

Ми можемо об'єднувати абсолютно неспоріднені класи в масиви чи колекції, орієнтуючись лише на те, який контракт вони підписали.

class Program
{
    static void Main()
    {
        // Біологія та Електроніка в одному масиві!
        IFlyable[] skyObjects = new IFlyable[] 
        { 
            new Bird(), 
            new Drone() 
        };

        foreach (var obj in skyObjects)
        {
            // Нам неважливо, хто це. Головне, що воно має метод TakeOff()
            obj.TakeOff(); 
            Console.WriteLine($"Ліміт висоти: {obj.MaxAltitude}м");
        }
    }
}

Колізія імен: Явна реалізація

Оскільки клас може реалізовувати багато інтерфейсів, виникає проблема: що, якщо два інтерфейси вимагають метод з абсолютно однаковим іменем?

public interface ISchool { void Study(); }
public interface IUniversity { void Study(); }

public class Student : ISchool, IUniversity
{
    // Неявна (звичайна) реалізація:
    // ОДИН метод обслуговує ОДРАЗУ ДВА інтерфейси.
    public void Study()
    {
        Console.WriteLine("Я просто навчаюсь...");
    }
}

А якщо бізнес-логіка вимагає, щоб поведінка у школі та університеті кардинально відрізнялася?

Явна реалізація (Explicit Implementation)

Для розділення логіки використовують явну реалізацію: перед іменем методу пишуть назву інтерфейсу. При цьому заборонено використовувати `public`.

public class Student : ISchool, IUniversity
{
    // Явна реалізація (прихована від об'єкта)
    void ISchool.Study() => Console.WriteLine("Вчу шкільну програму.");
    void IUniversity.Study() => Console.WriteLine("Слухаю лекції в універі.");
}

// ВИКОРИСТАННЯ:
Student s = new Student();
// s.Study(); // ❌ ПОМИЛКА! Метод прихований з відкритого API.

// Щоб викликати метод, треба привести об'єкт до конкретного інтерфейсу:
((ISchool)s).Study();     // Викличе шкільний метод
((IUniversity)s).Study(); // Викличе університетський метод

Системні контракти: IComparable<T>

Проблема сортування користувацьких об'єктів

Стандартний алгоритм Array.Sort() не знає, як сортувати об'єкти вашого класу Product. Що порівнювати: ціну чи назву? Виклик сортування призведе до крашу програми.

Рішення: Щоб "навчити" ваш клас взаємодіяти зі стандартними механізмами C#, він має підписати системний контракт — інтерфейс IComparable<T>.

21 / 24

Реалізація CompareTo

public class Product : IComparable<Product> // Вказуємо з ким будемо порівнювати
{
    public string Name { get; set; }
    public int Price { get; set; }

    // Метод має повернути: <0 (менше), 0 (рівні), >0 (більше)
    public int CompareTo(Product other)
    {
        if (other == null) return 1;

        // Делегуємо порівняння вбудованим типам C#
        return this.Price.CompareTo(other.Price); 
    }
}

// ТЕПЕР ЦЕ ПРАЦЮВАТИМЕ:
List<Product> list = new List<Product>();
// ... наповнення списку ...
list.Sort(); // CLR знайде інтерфейс і відсортує за ціною!

Сучасні фічі: Дефолтні методи (C# 8.0)

Раніше інтерфейси не могли містити жодного рядка логіки. У C# 8.0 додали можливість писати реалізацію методів за замовчуванням (Default Interface Methods). 

public interface ILogger
{
    void LogError(string msg); // Обов'язково реалізувати
    
    // Метод із тілом ПРЯМО В ІНТЕРФЕЙСІ!
    void LogInfo(string msg) 
    {
        Console.WriteLine($"[INFO]: {msg}");
    }
}

Навіщо це? Щоб дозволити розробникам бібліотек додавати нові методи у старі інтерфейси, не ламаючи при цьому існуючий код клієнтів. Якщо клієнт не реалізує метод сам — спрацює дефолтний.

23 / 24

Висновки

Поліморфізм як фундамент (virtual/override)

Замінює крихкі конструкції if-else на динамічне пізнє зв'язування. Робить архітектуру гнучкою та відкритою для нових фіч.

Абстракція (abstract)

Креслення для споріднених типів. Забороняє створення екземплярів базової логіки та жорстко вимагає від нащадків реалізації ключових методів.

Інтерфейси (interface)

Контракти поведінки (CAN-DO). На відміну від класів, об'єкт може підписати необмежену кількість інтерфейсів.

Явна реалізація

Потужний інструмент для вирішення колізій імен та приховування службових методів (як-от системні контракти) від публічного API.
